## Python Quickstart <a name="quick_start"></a>

Prerequisites: You need Python 3.10 or newer and `pip` for installing packages.

- **Create a Python virtual environment and activate it**

```bash
python3 -m venv .venv
source .venv/bin/activate
```

- **Install ADK**

```bash
pip install google-adk
```

- **Create a new project using `adk create` command**

```bash
adk create time_agent
```

This command creates the following files in time_agent folder:

```bash
time_agent/
    agent.py      # main agent code
    .env          # API keys or project IDs
    __init__.py
```

- **Update the agent definition:**

The `agent.py` file contains an agent definition. You can define tools for the agent to use.
Update `agent.py` code to include a `get_current_time` tool for use by the agent, as follows:

```python
from google.adk.agents.llm_agent import Agent

# Mock tool implementation
def get_current_time(city: str) -> dict:
    """Returns the current time in a specified city."""
    return {"status": "success", "city": city, "time": "10:30 AM"}

root_agent = Agent(
    model='gemini-flash-latest',
    name='current_time_agent',
    description="Tells the current time in a specified city.",
    instruction="""You are a helpful assistant that tells the current time in cities.
    Use the 'get_current_time' tool for this purpose.""",
    tools=[get_current_time],
)
```

- **Set your API key**

This agent network uses a Gemini model which requires an API key. Get an API key from
[Google AI Studio](https://aistudio.google.com/app/apikey) and write it into your `.env`
file via:

```bash
echo 'GOOGLE_API_KEY="YOUR_API_KEY"' > .env
```

- **Import your agent in `__init__.py`**

```python
from .agent import root_agent
```

- **Run your agent via command-line interface**

```bash
adk run time_agent
```
Image below shows a sample interaction with the agent.

![Agent interaction]({{ site.baseurl }}/images/time_agent_cli.png)

- **Run your agent via web interface**

The command below starts a web server with a chat interface for your agent. You can
access the web interface at http://localhost:8000. Select the agent at the upper
left corner and type a request.

```bash
adk web --port 8000
```

![Agent interaction]({{ site.baseurl }}/images/time_agent_web.png)

- **Run your agent by sending requests to an API server**

The command below will launch a local web server on http://localhost:8000

```bash
adk api_server --auto_create_session
```

The `--auto_create_session` flag automatically generates a new session if one
does not already exist when running the application. You can use `curl` commands
to interact with the local web server.

To check server's health or it's version:

```bash
curl -X GET http://localhost:8000/health
curl -X GET http://localhost:8000/version
```

To list the available agent network:

```bash
curl -X GET http://localhost:8000/list-apps
```

To send a request to `time_agent` agent network:

```bash
curl -X POST http://localhost:8000/run \
  -H "Content-Type: application/json" \
  -d '{
    "appName": "time_agent",
    "userId": "u_123",
    "sessionId": "s_abc",
    "newMessage": {
      "role": "user",
      "parts": [{"text": "Hello, can you help me?"}]
    }
  }'
```

## Manual Runner/Session Setup <a name="runner_session"></a>

When you run an agent network using the ADK CLI (such as `adk web`), the CLI handles a lot
of the boilerplate infrastructure under the hood -- it automatically instantiates a `SessionService`
to manage the sessions between users and agents, and a `Runner` that drives the agent's execution
loop, taking incoming user messages and invoking the necessary models or tools.

While the ADK CLI is an exceptional tool for rapid prototyping, debugging, and local development, it is
designed primarily as a developer sandbox. For production environments, we must explicitly define
a `SessionService` and a `Runner`, which we will do next.

- **Import the necessary packages**

```python
import asyncio

from google.adk.agents import Agent
from google.adk.runners import Runner
from google.adk.sessions import InMemorySessionService, Session
from google.genai import types  # For creating message Content/Parts
```

The `InMemorySessionService` is a simple implementation of `SessionService` that stores everything in
memory, suitable for testing and simple applications.

- **Instantiate a `SessionService` object**

```python
session_service = InMemorySessionService()

# Define constants for identifying the interaction context
APP_NAME = "current_time_app"
USER_ID = "user_001"
SESSION_ID = "session_001" # Using a fixed ID for simplicity

async def init_session(app_name:str, user_id:str, session_id:str) -> Session:
    session = await session_service.create_session(
        app_name=app_name,
        user_id=user_id,
        session_id=session_id
    )
    return session

session = asyncio.run(init_session(APP_NAME, USER_ID, SESSION_ID))
```

- **Instantiate a `Runner` object**

```python
runner = Runner(
    agent=current_time_agent, # The agent we want to run
    app_name=APP_NAME,   # Associates runs with our app
    session_service=session_service # Uses our session manager
)
print(f"Runner created for agent '{runner.agent.name}'.")
```

- **Interact with the agent**

```python
async def call_agent_async(query: str, runner, user_id, session_id):
    """Sends a query to the agent and prints the final response."""

    # Prepare the user's message in ADK format
    content = types.Content(role="user", parts=[types.Part(text=query)])
    final_response_text = "Agent did not produce a final response."  # Default

    # Key Concept: run_async executes the agent logic and yields Events.
    # We iterate through events to find the final answer.
    async for event in runner.run_async(
        user_id=user_id, session_id=session_id, new_message=content
    ):
        # is_final_response() marks the concluding message for the turn.
        if event.is_final_response():
            if event.content and event.content.parts:
                # Assuming text response in the first part
                final_response_text = event.content.parts[0].text
            elif (
                event.actions and event.actions.escalate
            ):  # Handle potential errors/escalations
                final_response_text = (
                    f"Agent escalated: {event.error_message or 'No specific message.'}"
                )

    # Return the value instead of just printing it
    return final_response_text


# We need an async function to await our interaction helper
async def run_conversation():
    response = await call_agent_async(
        "What is the time in London?",
        runner=runner,
        user_id=USER_ID,
        session_id=SESSION_ID,
    )
    print(f"Agent Response: {response}")


if __name__ == "__main__":
    try:
        asyncio.run(run_conversation())
    except asyncio.CancelledError:
        print("The agent task was cancelled externally (timeout or abort).")
    except Exception as e:
        print(f"An error occurred: {e}")
```

## Building an Agent Team <a name="multi_agent"></a>

So far we have built agent networks with a single agent that calls one (or two)
tools to look up time and weather. Building an agent network with multiple agents
offers several advantages, such as modularity, specilization, and efficiency.

In this section, we build an agent network with three agents. On top of the
`current_weather_agent`, we add two more agents: `greeting_agent` and `farewell_agent`.

- **Create a new project using `adk create` command**

```bash
adk create multi_agent
```

- **Create simple Python functions that serve as tools for new agents**

```python
def say_hello(name: str) -> str:
    """Provides a simple greeting message"""
    return f"Hello, {name}!"

def say_goodbye(name: str) -> str:
    """Provides a simple farewell message."""
    return f"Goodbye {name}! Have a great day."
```

- **Create `Agent` instances for new agents**

```python
greeting_agent = Agent(
    # Using a potentially different/cheaper model for a simple task
    model = "gemini-flash-latest",
    name="greeting_agent",
    instruction="You are the Greeting Agent. Your ONLY task is to provide a friendly greeting to the user. "
                "Use the 'say_hello' tool to generate the greeting. "
                "Make sure to pass the name the user provides to the tool. "
                "Do not engage in any other conversation or tasks.",
    description="Handles simple greetings and hellos using the 'say_hello' tool.", # Crucial for delegation
    tools=[say_hello],
)

farewell_agent = Agent(
    # Can use the same or a different model
    model = "gemini-flash-latest",
    name="farewell_agent",
    instruction="You are the Farewell Agent. Your ONLY task is to provide a polite goodbye message. "
                "Use the 'say_goodbye' tool to generate the farewell. "
                "Make sure to pass the name the user provides to the tool. "
                "Do not engage in any other conversation or tasks.",
    description="Handles simple farewells and goodbyes using the 'say_goodbye' tool.", # Crucial for delegation
    tools=[say_goodbye],
)
```

- **Define the root agent with new sub-agents**

```python
root_agent = Agent(
    model='gemini-flash-latest',
    name='current_time_agent',
    description="Tells the current time in a specified city and delegates greetings/farewells to specialists.",
    instruction="""You are the main Current Time Agent coordinating a team.
    Your primary responsibility is to provide the current time.
    Use the 'get_current_time' tool ONLY for specific current time requests (e.g., 'current time in London').
    You have specialized sub-agents:
    1. 'greeting_agent': Handles simple greetings. Delegate to it for these.
    2. 'farewell_agent': Handles simple farewells. Delegate to it for these.
    Analyze the user's query. If it's a greeting, delegate to 'greeting_agent'
    If it's a farewell, delegate to 'farewell_agent'
    If it's a current time request, handle it yourself using 'get_current_time'
    For anything else, respond appropriately or state you cannot handle it"""
    tools=[get_current_time],
    # Key change: Link the sub-agents here!
    sub_agents=[greeting_agent, farewell_agent]
)
```

- **Import your agent in `__init__.py`**

```python
from .agent import root_agent
```

- **Run your agent via command-line/web interface, or by sending requests to an API server**

The source code of the multi-agent agent network can be downloaded from [here]({{ site.baseurl }}/src/multi_agent/agent.py).

## ADK Tools <a name="tools"></a>

`google.adk.tools` is a Python package in ADK that provides tools an AI agent can use to perform actions beyond
generating text. The package contains the following tools:

- **FunctionTool**:	Wrap a Python function as a tool
- **AgentTool**; Expose another agent as a callable tool
- **McpToolset**: Integrate tools from MCP servers
- **OpenAPIToolset**: Generate tools from OpenAPI specifications
- **BaseTool**:	Base class for implementing custom tools
- **google_search**: Search the web using Google's built-in search

ADK also provides a `LangchainTool` adapter in (`google.adk.integrations.langchain.LangchainTool`), which allows
you to wrap existing LangChain tools and reuse their functionaluty without rewriting their functionality.

Below is an example of an agent calling Google search tool.

```python
from google.adk.agents import Agent
from google.adk.tools import google_search


# Define the single search-enabled agent
root_agent = Agent(
    name="search_assistant",
    model="gemini-flash-latest",
    description="A helpful assistant that can search the live web using Google Search.",
    instruction=(
        "You are a knowledgeable assistant with access to Google Search. "
        "When asked about current events, facts, or data requiring up-to-date information, "
        "use the Google Search tool to find accurate and grounded answers."
    ),
    tools=[google_search],
)
```

## MCP Tools <a name="mcp"></a>

The Model Context Protocol (MCP) is an open standard for connecting generative AI models to
external data sources, tools, and systems. Below we provide an example of an ADK agent acting
as ann MCP client using `McpToolset` -- You can also build an MCP server that wraps ADK tools
using `to_mcp_server`, but that is not covered here.

```python
# Allows you to interact with the underlying OS using Python
import os
# Core class in Google ADK to create LLM-powered agents
from google.adk.agents import LlmAgent

# Primary ADK integration class for MCP
from google.adk.tools.mcp_tool import McpToolset

# Imports the connection configuration wrapper specific to the ADK
from google.adk.tools.mcp_tool.mcp_session_manager import StdioConnectionParams
# Imports the core configuration class from Anthropic's official mcp Python library
from mcp import StdioServerParameters

TARGET_FOLDER = os.path.abspath("/Users/LarryBird")

root_agent = LlmAgent(
    model="gemini-flash-latest",
    name="filesystem_assistant",
    instruction="Help users manage local files.",
    tools=[
        McpToolset(
            # StdioConnectionParams: wrapper for Google ADK. It takes the low-level StdioServerParameters
            # and tells the ADK how to manage the connection session
            # StdioServerParameters: defines how to launch the server process at the operating system level
            connection_params=StdioConnectionParams(
                # npx stands for "Node Package Executive." It is a tool that comes bundled with Node.js
                # It allows you to download and run Node.js packages directly from the npm registry
                # without needing to manually install them globally on your machine
                # 1st arg: Automatically answers "yes" if npx prompts you to confirm downloading a package
                # 2nd arg: Name of the official Model Context Protocol server package hosted on npm
                # It is a pre-built server created by Anthropic that implements standard file-system
                # operations (like reading, writing, and listing directories) safely over the MCP protocol
                server_params=StdioServerParameters(
                    command="npx",
                    args=["-y", "@modelcontextprotocol/server-filesystem", TARGET_FOLDER],
                ),
            ),
            # Optional: Select specific tools exposed to the agent
            # Acts as a security or behavioral constraint. Even though the MCP
            # filesystem server might expose tools to write, delete, or move files,
            # this filter restricts the agent to only list_directory and read_file.
            # The agent can view files and folders, but it cannot edit or delete them
            tool_filter=["list_directory", "read_file"],
        )
    ],
)
```

- **Run your agent via command-line/web interface, or by sending requests to an API server**

## Miscellaneous <a name="miscellaneous"></a>

### Multi-Model with LiteLLM <a name="litellm"></a>

Google's ADK is natively optimized for Gemini, but it achieves full model-agnosticism
through a dedicated integration layer built on top of [LiteLLM](https://github.com/BerriAI/litellm).

Instead of passing only a model name string, we wrap the desired model identifier string within the
LiteLlm class. LiteLLM class also offers a failover mechanism via `fallbacks` parameter.

```python
from google.adk.agents.llm_agent import Agent
from google.adk.models.lite_llm import LiteLlm

root_agent = Agent(
    model=LiteLlm(
        model="openai/gpt-4o",
        num_retries=2,
        # Backup chain executed in order
        fallbacks=["anthropic/claude-3-5-sonnet-20241022", "ollama/llama3.3"],
    ),
    name="time_agent",
    instruction="You are a helpful assistant.",
    tools=[],
)
```

- **Besides `GOOGLE_API_KEY`, you must also set `OPENAI_API_KEY` and `ANTHROPIC_API_KEY`**

### Memory <a name="memory"></a>

Agent's memory in ADK is provided through *session state*. Session state is a Python
dictionary (`session.state`) tied to a specific user session (identified by app name,
user ID, and session ID). It persists information across multiple conversational turns
within that session. Agents and Tools can read from and write to this state, allowing
them to remember details, adapt behavior, and personalize responses.

Agents interact with Session State in two ways:

- **ToolContext** (Primary Method): Tools can accept a `ToolContext` object (automatically
provided by ADK for any parameter annotated ToolContext). This object gives direct access
to the session state via `tool_context.state`, allowing tools to read preferences or save
results during execution.

- **output_key** (Auto-Save Agent Response): An Agent can be configured with an
`output_key="your_key"`. ADK will then automatically save the agent's final textual
response for a turn into `session.state["your_key"]`.

### Callbacks <a name="callbacks"></a>

Callbacks let you intercept and customize execution at three levels: agent, model, and tool.

 - **Agent callbacks**
    - Execute before or after an agent runs
    - Examples: Check user permissions, or block unauthorized requests

- **Model callbacks**
    - Execute before or after an LLM call
    - Examples: Modify prompts, filter PII, or validate LLM outputs.

- **Tool callbacks**
    - Execute before or after a tool is called
    - Examples: Validate tool arguments, enforce API permissions, or return cached results

### Agent CLI <a name="cli"></a>

The **Agents CLI** tool set lets you plug ADK agent expertise into your favorite AI-coding
environments (e.g., Claude Code) to scaffold, build, test, evaluate, and deploy ADK agents.
Agents CLI consists of the following 7 **skill files**:

- workflow:	Manages the end-to-end development
- scaffold:	Handles initial project generation
- adk-code:	Teaches your coding agent how to write clean ADK code using Python
- eval:	Defines the quality assurance framework, and testing specifications for non-deterministic AI agents
- deploy: Manages infrastructure provisioning and cloud deployment options
- publish: Handles agent identity, registration, and discovery within enterprise ecosystems
- observability: Equips the agent with production-grade monitoring, and logging

### Workflows <a name="workflows"></a>

Graph-based agent workflows structure execution using specific compositional patterns. Workflows
provide the following advantage:

- Define precise logic: Explicitly map out routing logic to manage transitions between different nodes.
- Implement complex structures: Build agent workflows that support branching and state management.
- Run chains of functions without AI: Call agent tools and your own code without invoking a generative AI model.
- Enhance reliability: Improve the predictability of your agents by relying on structured node definitions rather than prompts alone.

The code below displays how to create a workflow where different agents and tools are called in a sequence.
Please read the inline comments for further explanantion.

```python
# For building AI agents
from google.adk import Agent
# For chaining agents into a pipeline
from google.adk import Workflow
# For managing messages
from google.adk import Event
# Pydantic's base class, used to define structured data schemas and validate data types in Python
from pydantic import BaseModel

# This agent generates a city name
city_generator_agent = Agent(
    name="city_generator_agent",
    model="gemini-flash-latest",
    instruction="""Return the name of a random city.
      Return only the name, nothing else.""",
)


# Defines a structured data model using Pydantic
# Any data conforming to this schema must contain two string fields: time_info and city
class CityTime(BaseModel):
    time_info: str  # time information
    city: str       # city name


# Time Lookup Helper Function
def lookup_time_function(node_input: str):
    """Simulate returning the current time in the specified city."""
    return CityTime(time_info="10:10 AM", city=node_input)


# AI agent responsible for generating the final report string
city_report_agent = Agent(
    name="city_report_agent",
    model="gemini-flash-latest",
    input_schema=CityTime,
    instruction="""Output following line:
    It is {CityTime.time_info} in {CityTime.city} right now.""",
)


# Helper function that receives the text output from the city_report_agent
# Wraps the text inside an Event object and appends "\n WORKFLOW COMPLETED."
# to signify that the pipeline has successfully finished execution
def completed_message_function(node_input: str):
    return Event(
        message=f"{node_input}\n WORKFLOW COMPLETED.",
    )


# edges: Defines the execution pipeline sequence
# 1. "START": Triggers the workflow
# 2. city_generator_agent: Generates a random city name
# 3. lookup_time_function: Takes that city name and creates a CityTime object with a simulated time
# 4. city_report_agent: Takes the structured object and formats it into a report sentence
# 5. completed_message_function: Wraps the final report in an Event object with a completion banner.
root_agent = Workflow(
    name="root_agent",
    edges=[
        ("START", city_generator_agent, lookup_time_function,
         city_report_agent, completed_message_function)
    ],
)
```

- **Run your agent via command-line/web interface, or by sending requests to an API server**

## Neuro San vs. ADK <a name="comparison"></a>

We Built a multi-agent flight search on both frameworks. Here’s what we found.

### TL;DR: Key Takeaway <a name="tldr"></a>s

- We found Neuro San and ADK very similar in features and design philosphy.
- Their main diference is that Neuro San defines agent networks in a text (.hocon) file, whereas ADK defines it in code
(Python, TypeScript, etc.).
- There are tradeoffs for these representions: Defining an agent network in a .hocon file could make the framework
easier to use for non-programmers, whereas defining the agent network in code could provide more expressiveness.
- Neuro San and ADK also handle senstivie data such as PII differently: ADK handles sensitive data via callbacks
before/after LLM models are used, whereas Neuro San has a dedicated channel called `sly_data`, where the
contents are kept out of reach of LLM models.

### Why Neuro San and ADK Are Worth Comparing <a name="comparing"></a>

ADK and Neuro San are both open source, multi-agent frameworks that allow users to quickly build sophisticated
multi-agent applications. They provide very similar features, though at times, the same feature is implemented
differently. Such differences could decide which framework should be used for which use case.

### Getting to Know Neuro San <a name="neurosan"></a>

Neuro AI system of agent networks (Neuro SAN) is an open-source, data-driven multi-agent orchestration framework designed
to simplify and accelerate the development of collaborative AI systems. It allows users -- from machine learning engineers
to business domain experts —- to quickly build sophisticated multi-agent applications without extensive coding, using declarative configuration files (in HOCON format).

Neuro SAN enables multiple large language model (LLM)-powered agents to collaboratively solve complex tasks, dynamically
delegating subtasks through adaptive inter-agent communication protocols. This approach addresses the limitations inherent
to single-agent systems, where no single model has all the expertise or context necessary for multifaceted problems.

### Getting to Know ADK <a name="adk"></a>

The Google Agent Development Kit (ADK) is an open-source framework designed for building, evaluating, and deploying
intelligent multi-agent AI systems. Moving beyond standalone LLM text generation, ADK provides a robust architectural
foundation enabling autonomous agents to reason, collaborate, utilize external tools, and manage complex, long-running
asynchronous workflows.

Key features of the framework include flexible multi-agent orchestration for hierarchical task delegation, deterministic
workflow loops, and native support for bidirectional real-time streaming. Additionally, ADK offers built-in primitives for
short-term session state and memory management, seamless tool integration, and a comprehensive developer UI with CLI tooling for step-by-step trace inspection and multi-turn evaluation.

### When to Use Each <a name="usage"></a>

Neuro San agent networks are defined in text (.hocon) files, allowing non-programmers to more easily prototype multi-agent
networks. Neuro San also offers a mechanism called `sly_data`, which facilitates safe handling and transfer of sensitive
data between agents without exposing it directly to any language models. ADK defines agent networks in code (multiple
programming languages like Python, TypeSCript, etc. are supported), which offers more expressiveness. ADK also offers more
built-in primitives to manage short-term conversational context, and long-term cross-session user memory.

So, if you are a non-programmer and deal with sensitive data, Neuro San may be a better choice. Whereas, if you need
maximum expressiveness and more built-in support for short/long term context, ADK may be a better choice.

### Neuro San Strengths <a name="ns_strength"></a>

- Data-Driven Configuration: Entire agent networks are defined declaratively via simple HOCON files, empowering
technical and non-technical stakeholders to design agent interactions intuitively.
- Extensible and Cloud-Agnostic: Compatible with a wide variety of LLM providers (OpenAI, Anthropic, Azure,
Ollama, etc.) and deployable in diverse environments (local machines, containers, or cloud infrastructures).
- Dynamic Agent Network Designer: Includes a meta-agent called the Agent Network Designer – essentially, an
agent that creates other agent networks. It can take a high-level description of a use-case as input and
generate a new custom agent network for it.
- Handling of sensitive data: Neuro San also offers a mechanism called `sly_data`, which facilitates safe handling
and transfer of sensitive data between agents without exposing it directly to any language models.

### Neuro San Limitations <a name="ns_limit"></a>

- Smaller ecosystem and community: While Neuro San community is growing fast, compared with Google ADK,
Neuro SAN has a smaller community, and fewer third-party integrations. Finding troubleshooting resources
and production examples may be more difficult.

- Programming language support: Neuro San is primarily a Python-native framework, and unlike ADK, does
not support TypeScript, Java, etc.

### ADK Strengths <a name="adk_strength"></a>

- ADK provides built-in multi-agent orchestration: ADK makes it easy to build complex agent systems using
    - Specialized agents: each agent is responsible for a specific task.
    - Hierarchical delegation: a parent agent decides which specialized agent should handle a request.
    - Sequential/parallel execution: ADK provides `SequentialAgent` and `ParallelAgent` that control execution order.
    - Workflow control: ADK provides `LoopAgent` for repeated execution.

- ADK provides much of the infrastructure needed to develop, test, and deploy AI agents
    - Tools: Mechanisms for agents to call Python functions, APIs, other agents, and external services.
    - Session management: To track conversation history and session state.
    - Memory: To store/retrieve information across different sessions, using a memory service.
    - Callbacks: Hooks to execute custom logic before or after agent, model, and tool operations.
    - Debugging: Local development UI (adk web) to inspect agent execution, events, tool calls, and state.
    - Evlauation: Framework for testing agent responses.
    - Deployment: Integration with deployment targets such as Vertex AI Agent Engine or Cloud Run.

### ADK Limitations <a name="adk_limit"></a>

- Model compatibility: Some ADK capabilities are tightly integrated with Gemini APIs. For example,
Gemini supports native bidirectional audio streaming. The ADK leverages this underlying Gemini API
feature seamlessly, resulting in low latency and a natural, conversational voice assistant loop in
just a few lines of code. When using OpenAI, Anthropic, or other models, their APIs might require
a multi-step, segmented pipeline (e.g., Speech-to-Text, then LLM text generation, and finally
Text-to-Speech); The ADK would have to manually orchestrate separate external services rather than
relying on a single native model capability.

- Tool Compatibility: Built-in tools such as `google_search` have API-specific restrictions and
combining built-in tools with custom functions can require special workarounds. For example,
suppose you are building a travel assistant agent that needs to search for current weather in
a destination city and then save that forecast directly into your SQL database. You use
`google_search` built-in tool for searching, and write a custom function called `save_to_database`
to save the results to database. Gemini's API, enabling built-in Google Search, sometimes restricts
how the model executes custom function calls in the exact same model turn. The Workaround is to
configure a multi-step orchestration pipeline: Turn 1: Pass the user's prompt to Gemini with
`google_search` enabled to fetch the live search data. Turn 2: Pass the summary into a separate
model call with your `save_to_database` tool active, allowing the model to generate the structured
parameters for your custom function.
